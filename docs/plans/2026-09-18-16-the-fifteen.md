## Decisions

**D1 — Ids follow the design's rule, with one correction.** `median-rent` becomes
**`median-rent-per-sqm`**. TAB4590 publishes rent per square metre, not per dwelling, and an id is
a permanent promise (`?i=`). Calling it `median-rent` would promise a number this project does not
have.

**D2 — `fertility-rate` is women's, and says so.** `TAB4805.Kon` has no total code. Summing men's
and women's summerad fruktsamhet would produce a number with no meaning, so the definition selects
`Kon=2` explicitly and the caveat says which measure this is. This is the one place where
`'total'` would have been actively wrong rather than merely unavailable.

**D3 — The labour-market band is 20–64, named in the caveat.** `TAB3200.Alder` offers twenty
overlapping bands and no total. 20–64 is Sweden's own convention for sysselsättningsgrad, and both
indicators from this table use it so they can be read against each other.
`Fodelseregion` takes its `tot`; `Kon` takes its `1+2`.

**D4 — `disposable-household-income` is NOT adjusted again.** TAB1492 is published in fixed prices.
Running it through `inflationAdjust` would deflate an already-deflated figure. It carries
`scale: 1000` (tkr to kronor) and nothing else, and the caveat states whose base year it is in —
SCB's, not this project's, which is a real difference from `median-income` and `house-prices`.

**D5 — Two units join the contract.** `count` rounds to 0 decimals, so a fertility rate of 1.45
would publish as `1`. `unit` is an enum, not a persisted byte, so adding to it is safe in a way
that touching `OBSERVATION_STATUS` never is. Added: `children-per-woman` (2 dp) and
`tonnes-per-resident` (2 dp), both with labels in both languages, following `per-km2`'s precedent
of a unit that names its own denominator.

**D6 — Two builders and one source flag, each arriving with the indicator that needs it.** Plan 14
proved that writing builders in advance is guessing.

- `Source.negate` — a source whose values are subtracted rather than added when several resolve
  into the same cell. `natural-change-rate` is then the existing `ratio` builder over a numerator
  of births minus deaths, with no new arithmetic at all.
- `{ kind: 'quotient', of, by }` — one published series over another. `house-price-to-income`.
- `{ kind: 'difference', of, minus }` — one published series minus another.
  `post-secondary-education-gap`.

**D7 — The facts engine sees all twenty-seven, with re-derived noise bounds.** Design D4. ADR-0003's
noise bound is per indicator in that indicator's own unit and cannot be inherited.

**D8 — DESIGN §8's sentence about nature data is wrong and gets corrected.** `TAB4357` publishes
municipal greenhouse gases. Design D5.

## Tasks

### Task 1 — The contract learns two units

`shared/pantry.ts`: `children-per-woman` and `tonnes-per-resident` in the `unit` enum and in
`UNIT_DECIMALS`. `src/i18n/format.ts`: a label in both languages. `src/pantry-format.test.ts` pins
the decimals map and must be updated with it.

**Acceptance:** `yarn typecheck` passes with both languages; the pantry is untouched (no indicator
uses them yet); `src/pantry-format.test.ts` asserts the new entries.

### Task 2 — `Source.negate`, and the three new spec kinds

TDD: `kitchen/src/indicators/{source,define}.test.ts` first, against fabricated metadata, then the
implementation. No indicator uses them yet, so the tests are the only caller and must be real.

**Acceptance:** `public/pantry/` byte-identical (nothing uses the new code); a negated source
subtracts; `quotient` and `difference` refuse a series that has not been built yet, naming it,
the way `ratio` already does.

### Task 3 — The seven direct indicators

`fertility-rate`, `dependency-ratio`, `employment-rate`, `unemployment-rate`,
`taxable-income-per-resident`, `disposable-household-income`, `median-rent-per-sqm`.

Each: a declaration, prose in both languages, a registry entry, `yarn kitchen fetch` for its table,
then a headline figure **read off the published pantry and checked against a second source** —
either SCB's own Riket row or a municipality whose value can be reasoned about.

**Acceptance:** `check.ts` passes, including 290 municipalities per indicator; a second `publish`
is byte-identical to the first; each has a row in `src/indicators.semantics.test.ts`.

### Task 4 — The four rates

`natural-change-rate`, `dwellings-completed-rate`, `dwellings-per-1000`,
`greenhouse-gas-per-resident`. Each divides by population, so each depends on population being
built first — `registry.load-order.test.ts` is the guard.

**Freeze size is measured before fetching**, per the design's risk 1: TAB960's full cube is
3,627,936 cells and TAB1264's is 1,351,584. Selecting the age and sex totals server-side takes both
to 290 × years. If a measured selection is still large, the selection gets redesigned, not absorbed.

### Task 5 — The two shares and the two splits

`share-houses`, `share-rentals` over `TAB824`; `post-secondary-education-women` and `-men` over the
already-frozen `TAB3981`, which means **no new fetch**.

`TAB824` has no total on either `Hustyp` or `Upplatelseform`, so both need a `SUM_SAFE` entry with
its reason written out, exactly as TAB638's and TAB3981's are.

### Task 6 — The two derived

`post-secondary-education-gap` and `house-price-to-income`, from the pantry alone.

### Task 7 — The site carries twenty-seven

Measure what the design's risk 2 predicted: the profile renders one sparkline per indicator, and
27 is 2.7× ten. Lighthouse median of three, against the budget. The facts engine's per-indicator
noise bounds (D7).

### Task 8 — The record

ADR-0016 with D1–D8; `docs/kitchen.md`; the DESIGN §8 correction; the slice design's §4 table
reconciled with what actually shipped.

**Seventeen indicators, not fifteen**, and the reason is in [D1](../decisions/0016-the-fifteen.md).

**Every published figure reconciled against a second read.** Either a separately shaped request
through a throwaway raw directory, or hand arithmetic over raw counts and the published
population. Stockholm 2024's natural change is 11,430 births less 5,850 deaths over 995,574
residents; the pipeline publishes 5.6 and so does the arithmetic. Not one figure disagreed, so the
stop condition that would have halted this plan never fired.

**The design's two risks, both measured rather than argued.** TAB960's full cube is 3,627,936
cells; selecting the age and sex totals server-side takes it to 33,060, and the whole slice adds
3.1 MB against the 48 MB TAB638 already costs. Twenty-seven sparklines cost a municipality page
four Lighthouse points — 86 at ten indicators, 82 at twenty-seven, same URL, same machine, spreads
overlapping — and the root page nothing at all, because plan 13's split means a visitor loads the
index and one series whatever the count.

**Three things this plan asserted and got wrong**, each corrected where it was written:

- The education splits needed a fetch after all. `Kon=2` is a different selection from `Kon=1+2`,
  and only the latter was frozen.
- `NATURAL_YEARS = YEARS` stopped the whole suite loading. `coverage` is read when
  `Indicator.parse` runs at module load and `population.ts` is mid-cycle then — decision 0014 D4's
  hazard exactly, which is why every other indicator writes its own range out.
- House prices' extreme denominator is 285 in both 2024 and 2025. The plan's guess that it moved
  with the year was wrong; the municipality at the bottom moved, from Åsele to Malå.

## Stop conditions

- A table turns out not to carry 290 municipalities after all → drop that indicator, say so.
- A freeze is disproportionate → redesign the selection; if it cannot be, drop and record.
- A published figure cannot be reconciled against a second source → **stop and report**. A number
  nobody can check is the one thing this project must not publish.
- The performance budget falls below its floor → report the measurement rather than raising the
  floor.
