# Plan 9: A page per municipality

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A link to Malmö should show Malmö when it is pasted into a chat, not the site's front page.

**Architecture:** 580 pre-rendered HTML files, two per municipality, each carrying its own title, description and preview card. The application behind them is unchanged: every page loads the same bundle and the same pantry, and the path is read as a piece of state exactly as `?m=` already is.

**Tech stack:** No new runtime dependency. The preview cards are rasterised with Playwright, which is already here for the browser tests.

**Spec:** [docs/DESIGN.md](../DESIGN.md), sections 3 (the website), 7 (scope).

## What was checked before this was designed

### SVG does not work as a preview image

The roadmap's guess was that "SVG rendered at build time is the obvious candidate and needs checking against what social platforms actually accept". Checked, on 2026-09-15:

- **Facebook's own image documentation** states the dimensions (at least 1200 × 630, minimum 200 × 200, 8 MB ceiling, 1.91:1) and **says nothing at all about formats**.
- **Slack's unfurling documentation** says it "looks for common OpenGraph and X … Card metadata" and states no format requirement either.
- **X's card documentation is behind a paywall** (HTTP 402) and could not be read.

So no platform documents SVG support, and every secondary source says SVG is ignored or fails outright. Shipping SVG would be betting on undocumented behaviour that three primary sources decline to promise. **The cards are rasterised to PNG.**

### Rasterising is cheap; storing is not free

Measured with Playwright, rendering a 1200 × 630 card and screenshotting it:

|           | measured    |
| --------- | ----------- |
| per card  | **35 ms**   |
| 290 cards | ~10 s       |
| mean PNG  | **26.8 kB** |
| 290 PNGs  | **7.6 MB**  |

### Two facts about the names

- **Municipality names are identical in Swedish and English** — all 290 of them. So one card serves both languages, which halves 580 images to 290.
- **Slugs collide.** Transliterating å→a turns **Håbo** (Uppsala county) and **Habo** (Jönköping county) into the same slug. They are two real, separate places.

## The decisions this plan makes

**D1 — The path is `name-code`: `/en/stockholm-0180/`.** Chosen by the architect. Readable and unique _by construction_, so the Håbo/Habo collision cannot happen and neither can a future one: no SCB rename can ever turn a working link into a 404, or into somebody else's page. Parsing is trivial — the last four digits are the code, and the slug is decoration the parser does not trust.

The alternatives and why not: the real name with its å and ö (`/en/håbo/`) is prettier and honest, but "å" is either one code point or an "a" plus a combining ring, and on static hosting a request in the form the file was not written in is a plain 404 with nothing to catch it. Slug-alone-with-suffix-where-needed is prettiest for 288 of 290, but _which_ URLs need the suffix depends on the data, so a rename could change a link that already exists.

**D2 — `?m=0180` keeps working, for ever.** DESIGN calls the URL grammar "final in the first slice so nothing shared ever breaks", and this plan adds to that grammar rather than replacing it. Both forms parse. The path form is what the site produces and what `rel=canonical` points at; the query form is what already exists in the world.

**D3 — One card per municipality, with no figures on it.** Chosen by the architect. The card shows the municipality's name and the site's name, and nothing that changes when SCB publishes — so it is generated once and the monthly refresh never rewrites 290 binaries. A card carrying a headline figure would cost the same 7.6 MB and then churn all of it every month, roughly 90 MB of git history a year for a number nobody reads twice.

**D4 — The cards are generated by an explicit command, never by `yarn build`.** Text rendering differs between macOS and Linux, so the same card built on a laptop and in CI will not be byte-identical. Wiring generation into the build would mean every CI run produced a diff. `yarn cards` regenerates them deliberately; the committed PNGs are the artefact.

This also keeps them clear of the pantry's determinism check, which covers `public/pantry/` only. The cards are not pantry data — they are derived from it, like the site's own bundle.

**D5 — The 580 pages are written after the build, not by Vite.** Vite would need 580 entries in `rollupOptions.input`, and each is the same document with three strings changed. A post-build step copies the language's entry page and rewrites its head, which is a few milliseconds and leaves the build config as it is.

**D6 — The dev server serves the same paths.** A Vite middleware answers `/{lang}/{slug}-{code}/` with the language's entry page, so `yarn dev` and `dist/` behave the same way. Without it every one of these URLs would 404 in development and work in production, which is the worst way round.

**D7 — No new state.** The path selects a municipality and nothing else. Indicator, year, compare, view and table stay in the query, on top of the path: `/en/stockholm-0180/?i=mean-age&y=1990`.

## The shape of a page

```html
<html lang="en">
  <title>Malmö · Sweden's municipalities in data</title>
  <meta
    name="description"
    content="Malmö in ten measures from Statistics Sweden, year by year from 1968 to today."
  />
  <link rel="canonical" href="/en/malmo-1280/" />
  <link rel="alternate" hreflang="sv" href="/sv/malmo-1280/" />
  <link rel="alternate" hreflang="en" href="/en/malmo-1280/" />
  <meta property="og:title" content="Malmö · Sweden's municipalities in data" />
  <meta property="og:image" content="/share/1280.png" />
  <meta name="twitter:card" content="summary_large_image" />
</html>
```

`og:image` needs an absolute URL to work, and the domain is not decided yet — [docs/plans/README.md](README.md) lists the project name as blocking it. The generator takes a base URL from one place and writes a root-relative path when there is none, so the day the domain exists this is one constant, not 580 files.

## Tasks

### Task 1 — The grammar

- [ ] `shared/slug.ts`: `slugFor(name, code)` and `parseSlug(segment)`.
- [ ] Transliterate å, ä, ö, é and strip anything else to `a-z0-9-`; append the four-digit code.
- [ ] `parseSlug` trusts **only** the code and ignores the slug, so a renamed municipality keeps its old links working and a hand-typed slug cannot point somewhere else.
- [ ] Tests: Håbo and Habo get different paths; every one of the 290 is unique; a wrong slug with a right code still resolves; a right slug with no code does not.

### Task 2 — Reading the path

- [ ] `parseState` reads the municipality from the path when there is one, and from `?m` otherwise.
- [ ] `toUrl` writes the path form and drops `?m`.
- [ ] A path and a conflicting `?m` is resolved one way, deliberately and tested — the path wins, because it is what the server used to choose the document.
- [ ] Tests: both forms parse to the same state; every existing `?m=` link in the repo still resolves; a code that is not in the pantry falls back rather than throwing.

### Task 3 — The dev server

- [ ] A Vite plugin serving `/{lang}/{slug}-{code}/` from the language entry page.
- [ ] Unknown codes 404 in development exactly as they will in production, rather than silently rendering the front page.

### Task 4 — The cards

- [ ] `tools/build-cards.mjs`, run as `yarn cards`: 290 PNGs into `public/share/`.
- [ ] Name and site name only — nothing that changes when the data does (D3).
- [ ] Both light and dark are irrelevant here: the card is its own artwork and picks one palette.
- [ ] Run it, commit the PNGs, record the real total size.

### Task 5 — The pages

- [ ] `tools/build-pages.mjs`, run after `vite build`: 580 files, each from its language's entry page with title, description, canonical, hreflang, og and twitter tags rewritten.
- [ ] The base URL comes from one constant; with none, the tags are root-relative.
- [ ] Tests over the generated output: 580 files exist, each names its own municipality, each points at an image that exists on disk, each declares the right `lang`.

### Task 6 — The site knows where it is

- [ ] The document title already comes from the state; confirm a direct load of `/en/malmo-1280/` produces the same title the pre-rendered file carries, or the tab changes the moment the bundle boots.
- [ ] The profile panel opens for the municipality in the path on first paint.

### Task 7 — In a browser
