# Plan 8: The morph

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The last piece of the original vision. The 290 municipalities stop cutting between two views and travel between them — the map's shapes flowing into the cartogram's bubbles and back.

**Architecture:** One SVG, one set of 290 `<path>` elements, and a `t` between 0 and 1. `MapView` and `Cartogram` become the two ends of the same component rather than two components that replace each other.

**Tech stack:** Unchanged. No new dependency — the interpolation is a lerp between two point lists, and the browser's own path measurement does the sampling.

**Spec:** [docs/DESIGN.md](../DESIGN.md), sections 3 (the website), 5 (accessibility), 9 (still open — both questions below are settled here).

## The two questions DESIGN parked, answered by measurement

Section 9 left these "deliberately undecided until we prototype". A prototype was built on 2026-09-15 against the real geometry and run in all three engines, and under Chromium's CPU throttling as a stand-in for a mid-range phone.

### Does the morph need a Canvas layer beneath the SVG? **No.**

Per-frame work, 290 shapes, against a 16.7 ms budget. Chromium under CDP CPU throttling — 4× to 6× is the usual stand-in for a mid-range phone:

| Approach         |   1× |   2× |    4× |        6× |       10× |
| ---------------- | ---: | ---: | ----: | --------: | --------: |
| 16-point SVG     | 0.97 | 1.97 |  3.98 |      5.94 |      10.4 |
| **32-point SVG** | 1.59 |  3.4 |  6.67 |     10.12 | **17.47** |
| 64-point SVG     | 2.84 | 5.98 | 12.06 | **18.01** | **34.67** |
| 32-point Canvas  | 1.31 | 2.69 |  5.35 |      8.07 |     13.48 |
| transform only   | 0.54 | 1.09 |  2.22 |      3.17 |      6.06 |

Bold misses the budget. **SVG at 32 points holds 60 fps at 6× with 40% of the frame to spare**, and only fails at 10× — a device slower than the plan needs to serve. Canvas buys between 1.2× and 2.9× depending on engine, which is real and is not needed.

It would also cost something. DESIGN's own constraint is that a Canvas sits _beneath_ the SVG focus and ARIA layer, never replacing it — so the SVG with its 290 focusable shapes has to exist either way, and adding Canvas means maintaining two renderers of the same 290 things and keeping them in step. That is a large permanent cost for headroom the measurements say is already there.

Unthrottled, all three engines pin to exactly 16.7 ms on every variant — they are all waiting for the display rather than for the work. The throttled column is the one that decides anything.

### Bubbles or a hexagon grid? **Bubbles.**

Not a performance question after all, which is why no prototype was built for it. The cartogram has shipped as bubbles since Plan 4, addressable at `?v=cartogram`, with a keyboard cone measured against that layout (50°, `CARTOGRAM_CONE_COS`) and its own tests. **A morph has to end at the view that exists**, or it is a transition between the map and a third thing nobody can otherwise reach. Hexagons would mean a new layout in the kitchen, a new published file, a re-measured keyboard cone, and the replacement of a view that already works — for an aesthetic preference, not a measured gain. Recorded as decided rather than left open.

## The decisions this plan makes

**D1 — SVG, no Canvas.** Measured above. If a real device ever proves slower than 6×, the fallback is fewer sample points, not a second renderer: 16 points still fits at 10×.

**D2 — 32 sample points per shape.** The rule is "the most faithful resampling that still fits the budget on a phone-class device", and 32 is it — 64 misses at 6×. Not chosen for looks: 16 looks nearly the same, and would have been chosen had 32 not fitted.

**D3 — Bubbles, because the morph must end at the view that exists.**

**D4 — Resample in the site, not the kitchen.** 22–39 ms once per load, against roughly 150 kB added to a 1.06 MB pantry if the sampled points were published — and the sampling depends on the browser's own path measurement, which the kitchen has no DOM to run. The cost is paid once, off the critical path, after the map is already interactive.

**D5 — The two frames must be reconciled before anything can move.** The map is projected into a 1000×2000 frame; the bubble layout lives in a unit square whose aspect ratio is not 1:2. Scaling x by 1000 and y by 2000 stretches the layout and pushes it off the bottom — which the prototype did, and which is visible in its stills. The cartogram's circles get placed into the map's frame by one uniform scale and one offset, computed from the layout's own bounds, so a circle stays a circle.

**D6 — Reduced motion cross-fades and never moves.** Already the rule for the map's colour transitions; the morph is a much bigger movement and the same rule binds harder. `prefers-reduced-motion` gets an opacity swap with no interpolation at all — not a shorter morph.

**D7 — The morph is a transition, not a third view.** The URL keeps `?v=map` and `?v=cartogram`; nothing addresses a half-morphed state, because a link to "40% of the way to the bubbles" is not a view anybody wants to share. Everything the visitor can reach is still exactly one of the two.

## The shape of it

```ts
// src/map/morph.ts
type MorphPair = {
  code: string
  /** The real path data, used at rest at each end. */
  mapD: string
  cartogramD: string
  /** 32 sampled points at each end, used only while moving. */
  from: Point[]
  to: Point[]
}
morphD(pair, t): string   // t === 0 -> mapD, t === 1 -> cartogramD, else the lerp
```

**The ends are the real geometry, not the resampling.** At rest the map draws its full 194-point coastline and the cartogram draws a true circle; the 32-point proxies exist only while `0 < t < 1`, where nobody can see the difference. That is what lets the sample count be chosen for the frame budget rather than for fidelity.

## Tasks

### Task 1 — One frame for both layouts

- [ ] `src/map/frame.ts`: place the bubble layout inside the map's 1000×2000 frame with one uniform scale and one offset, from the layout's own bounds.
- [ ] Tests: a circle stays circular (equal x and y scale); every circle lands inside the frame; the result is stable for a given layout.

### Task 2 — Sampling and the lerp

- [ ] `src/map/morph.ts`: `sampleOutline(d, n)` via `getTotalLength`/`getPointAtLength`, `sampleCircle(c, n, startAngle)`, and `morphD(pair, t)`.
- [ ] The circle's start angle is chosen from the shape's own first point, so a municipality does not spin on its way over.
- [ ] `t === 0` and `t === 1` return the real path data, never the resampling.
- [ ] `SAMPLE_POINTS = 32`, with the throttling table in its comment so the number is evidence.
- [ ] Tests: point counts; both ends exact; a midpoint is between the two; the no-spin property; a multi-subpath island municipality samples without throwing.

### Task 3 — The clock

- [ ] `src/state/useMorph.ts`: drives `t` from 0 to 1 on a `requestAnimationFrame` loop with an ease, and cancels cleanly when the view changes mid-flight.
- [ ] `prefers-reduced-motion` returns t as an immediate 0 or 1 and never schedules a frame (D6).
- [ ] Tests with fake timers: it reaches 1; reversing mid-morph does not jump; reduced motion never calls rAF.

### Task 4 — One component, two ends

- [ ] `MapCanvas.tsx` renders the 290 paths once and morphs them, replacing the pair of components that swap.
- [ ] Everything that already works keeps working, and this is the whole risk of the task: the roving tabindex over 290 shapes, the two-tone focus ring, the arrow-key cone (45° on the map, 50° on the cartogram), the fills, the status patterns, the accessible names, the live region.
- [ ] The existing `MapView` and `Cartogram` tests must keep passing against it, rewritten only where they name a component rather than a behaviour.

### Task 5 — Keeping the keyboard honest through the movement

- [ ] Arrow keys during a morph use the cone of the end being travelled to, so a keypress mid-flight cannot land somewhere neither layout would have sent it.
- [ ] Focus is never lost when the view changes: the focused municipality stays focused and its ring travels with it.
- [ ] Tests for both, including a keypress while `0 < t < 1`.

### Task 6 — In a browser

- [ ] `e2e/morph.spec.ts`: switching views moves the shapes rather than replacing them; focus survives; with reduced motion nothing moves and the end state is still correct.
- [ ] Re-run the axe scan on both ends and mid-morph.
- [ ] Full suite in three engines, and Lighthouse — the performance budget is the regression alarm for D1.
