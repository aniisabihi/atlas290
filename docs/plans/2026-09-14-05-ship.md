# Plan 5: Ship

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Put the thing on the internet, and make it stay correct without anybody watching. Continuous integration that actually runs the tests, real browsers checking the keyboard, an automated accessibility audit, a performance budget with a number in it, a monthly job that notices when SCB publishes and opens a pull request, a notices page that honours every licence, and a deploy that only happens when all of that is green.

**Architecture:** Nothing about the site changes. This plan is scaffolding around it: one CI workflow, one scheduled workflow, one static page, and a handful of dependency corrections.

**Spec:** [docs/DESIGN.md](../DESIGN.md), sections 5 (accessibility), 6 (testing), 7 (scope).

## The gap this plan closes

Plans 2, 3 and 4 each ended by noting that **no CI runs on this repository**. Seven hundred and thirty-five tests exist and none of them has ever run anywhere except a laptop. Every pull request so far has been merged on the strength of a local run reported in prose. That is the first task, and everything else in this plan depends on it.

## Global constraints

- **Free, with no paid dependency and no trial.** Verified below, from primary sources, before this plan was written.

- **Never handle the architect's credentials.** The Cloudflare API token is created by them, in their account, and stored as a GitHub secret. This plan documents the exact steps and the minimum permissions; it does not perform them and must not ask for the value.
- Both languages on any new visible string.
- Conventional Commits. Trailer: `Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`.
- Never `--no-verify`. Work on `feat/plan-05-ship`; do not push, merge or change branches from inside a task.

### Two dependency errors found while checking the licences

- **`d3-scale` is used by nothing.** Plan 3 replaced `scaleThreshold` with `classOf` in `src/data/select.ts` and the dependency stayed. Grep finds no import of it anywhere in `src/`, `shared/` or `kitchen/`.
- **`d3-force` is used only by the kitchen** (`kitchen/src/geometry/bubbles.ts`), so it is a build-time dependency declared as a runtime one.

Both matter here beyond tidiness: the notices page has to say what actually ships, and it cannot be right while the manifest is wrong.

### Task 1: The tests finally run somewhere

**Files:**

- Create: `.github/workflows/ci.yml`

Three plans have shipped on the strength of a local test run reported in prose. This is the task that ends that.

- [ ] **Step 1: Write the workflow**

On `pull_request` and on `push` to `main`. One job: check out, set up Node 22 with Yarn caching, `yarn install --immutable`, then `yarn typecheck`, `yarn lint`, `yarn test`, `yarn build`.

`--immutable` matters: it fails if `yarn.lock` would change, so a pull request cannot quietly install something different from what was reviewed.

- [ ] **Step 2: Add the pantry determinism check**

The kitchen's promise is that publishing twice from frozen data gives byte-identical output. Run `yarn kitchen publish` and fail if `git status --porcelain public/pantry/` is non-empty. That promise has been checked by hand at the end of three plans; from here it is checked on every push.

This step must run with **no network**, which is what `publish` already enforces internally.

- [ ] **Step 3: Prove the workflow can fail**

A CI job that passes is not evidence until it has been seen to fail. Break something small on the branch — a deliberate type error — push, confirm the run goes red, revert, confirm it goes green. Record both run URLs in the report.

- [ ] **Step 4: Commit**

`ci: run the tests on every pull request`

### Task 2: Real browsers, and the keyboard question I could not answer

**Files:**

- Create: `playwright.config.ts`, `e2e/` specs
- Modify: `package.json`, `.github/workflows/ci.yml`

Plans 3 and 4 both ended with the same admission: keyboard behaviour was verified **in WebKit only**, because that is the browser in the tool I had. Safari does not move focus to non-form elements with Tab unless full keyboard access is on, and I could not test Chromium or Firefox at all. This task answers it properly.

- [ ] **Step 1: Install Playwright and configure three browsers**

Chromium, Firefox and WebKit. `webServer` runs `yarn build && yarn preview` so the tests exercise the built site rather than the dev server — the built site is what visitors get.

- [ ] **Step 2: Write the specs that matter, not a smoke test**

The value here is entirely in what only a real browser can answer:

- **Tab reaches the map in every browser**, and the page is the expected number of stops deep. This is the exact claim I could not make.
- **Arrow keys move the focus ring**, and the ring is visibly drawn — assert the focus ring element exists after a real `ArrowUp`, which is the Plan 3 defect in test form.
- Clicking a municipality focuses it, so arrows work afterwards.
- The year slider responds to a real drag and to arrow keys — jsdom implements neither, so Plan 3's slider tests had to drive `change` directly and explicitly said so.
- A deep link restores its view: open `?i=house-prices&y=1990&m=0184` and assert the profile shows Solna.
- The root redirect sends a browser to its own language, tested with an explicit locale.
- Switching to the cartogram swaps the view and keeps the selection.

- [ ] **Step 3: Run them, and record what differs between browsers**

Expect differences. Report them honestly: if Tab does not reach SVG paths in some browser, that is a finding to fix or to document, not to hide. **Do not weaken a test to make a browser pass.**

- [ ] **Step 4: Add to CI and commit**

Cache the browser binaries by Playwright version. Upload the report as an artifact on failure.

`test(e2e): check the keyboard in three real browsers`

### Task 3: Accessibility checked by a machine, every time

**Files:**

- Create: `e2e/accessibility.spec.ts`
- Modify: `package.json`

`@axe-core/playwright` on the real built pages. It catches contrast, names, roles and structure — perhaps a third of what matters, which is why Task 7 still does a manual pass.

- [ ] **Step 1: Write the scan**

Scan each meaningful state, because they render different DOM: the plain map, the cartogram, the table, a municipality selected with its profile open, a comparison, and an out-of-coverage year. Both languages for at least one of them.

Run with WCAG 2.2 AA tags. **Zero violations, and no disabled rules.** If a rule fires, fix the page; if a rule is genuinely wrong about this page, disable it in one place with a written reason and say so in the report.

- [ ] **Step 2: Run it and fix what it finds**

Report every violation found and what was done about it. A clean first run should be treated as suspicious and checked — deliberately break something (remove a label) and confirm the scan goes red.

- [ ] **Step 3: Commit**

`test(e2e): fail the build on an accessibility violation`

### Task 4: A performance budget with a real number in it

**Files:**

- Create: `.lighthouserc.json` or an equivalent budget file
- Modify: `.github/workflows/ci.yml`

- [ ] **Step 1: Measure before deciding**

Run Lighthouse against the built site and record the actual numbers. A budget invented before measuring is either trivially met or immediately broken, and neither teaches anybody anything.

- [ ] **Step 2: Set the budget just above where it sits**

Performance, accessibility and best-practices thresholds, plus a transferred-bytes budget for script. The point is to notice a regression, not to chase a hundred.

The pantry is 1.05 MB uncompressed and the site fetches it on load; that is a deliberate architectural choice from Plan 3 (275 kB gzipped, cheaper than per-indicator fetching) and the budget must accommodate it rather than pretend otherwise.

- [ ] **Step 3: Commit**

`ci: a performance budget measured rather than guessed`

### Task 5: Say what ships, and ship only what is used

**Files:**

- Modify: `package.json`
- Create: `src/components/Notices.tsx` and its test, or a static notices page

- [ ] **Step 1: Fix the dependency manifest first**

Remove `d3-scale` and `@types/d3-scale` — nothing imports them. Move `d3-force` and its types to `devDependencies` — only the kitchen uses it. Then `yarn build` and `yarn test` to prove nothing depended on either being where it was.

- [ ] **Step 2: Write the notices page**

Reachable from the footer, in both languages, listing:

- **The data.** SCB, CC0. State the two terms that actually bind, in their own words: SCB asks that you **do not** cite them as the source for figures you derived yourself, and that you do not present the service as an official cooperation with SCB. Both are already honoured by the pantry's provenance manifest; the page says so out loud.
- **The boundaries.** SCB's CC0 shapefile, with the generalisation caveat: simplified for thematic maps, not suitable for analysis.
- **The libraries.** Every package in the runtime dependency tree, with its licence. Over-listing is harmless; under-listing is a licence violation, so err towards listing.
- **The code.** MIT, with a link to the repository.

- [ ] **Step 3: Test it against the manifest, not against a copy**

A test that reads `package.json`'s runtime dependencies and asserts each one appears on the notices page. A notices page maintained by hand drifts the first time somebody adds a dependency; this makes that a failing test instead.

- [ ] **Step 4: Commit**

`feat(site): a notices page that names every licence, checked against the manifest`

### Task 6: The monthly refresh

**Files:**

- Create: `.github/workflows/refresh.yml`

Once a month: fetch from SCB, republish, and open a pull request if anything changed. A data refresh arrives as a readable diff to review rather than a silent change to a live site.

- [ ] **Step 1: Write the workflow**

Schedule plus `workflow_dispatch`, so it can always be run by hand. Steps: install, `yarn kitchen fetch`, `yarn kitchen publish`, then open a pull request if `git status --porcelain` shows changes under `kitchen/raw/` or `public/pantry/`.

Use `peter-evans/create-pull-request` or an equivalent pinned to a commit SHA rather than a moving tag — a workflow with write access that follows a mutable tag is a supply-chain risk, and this one has write access by definition.

- [ ] **Step 2: Keep it alive, deliberately**

**Verified:** a public repository's scheduled workflows are disabled after **60 days without repository activity**, and the docs do not define what counts as activity. So the job writes a dated line to a log file and commits it on every run, whether or not the data changed. That is a real commit every month, which is activity under any reading.

Say in the workflow file why that commit exists. A future reader finding a bot committing a log line every month deserves to know it is load-bearing rather than noise.

- [ ] **Step 3: Handle SCB being unavailable**

The fetch talks to a real service that can be down or slow. The job must fail loudly rather than open a pull request deleting data. Guard it: if the fetch fails, stop; if the published pantry would **lose** more than a trivial number of values, stop and say so.

- [ ] **Step 4: Run it once by hand and report what happened**

`workflow_dispatch` it. Expect no data change — the pantry was published today — so the interesting outcome is that it runs clean, commits the log line, and opens no pull request.

- [ ] **Step 5: Commit**

`ci: a monthly refresh that opens a pull request and keeps itself alive`

### Task 7: The manual accessibility pass

**Files:**

- Create: `docs/accessibility.md`

axe finds perhaps a third of what matters. This is the rest, done by hand and written down.

- [ ] **Step 1: Do the pass and record it honestly**

Against WCAG 2.2 AA, plus the Chartability questions DESIGN commits to for a data visualisation. At minimum:

- Keyboard only, start to finish, in each of the three browsers, including the profile, the comparison, the table and the cartogram.
- Every interactive element reachable, and focus visible on all of them.
- Reflow at 320 px and at 400% zoom.
- The map's meaning available without colour: the legend, the announcement and the table twin.
- Text contrast, including the muted text the token test already checks.
- `prefers-reduced-motion` honoured everywhere.
- A screen-reader pass with VoiceOver on the map, the year slider, the search combobox and the profile.

- [ ] **Step 2: Record what fails, not only what passes**

Anything found goes in the document with a severity and either a fix in this plan or a named reason for deferring. **A document that says everything passed is not credible** and will not be believed by the next reader, including a future me.

The known one to start from: Plan 4 recorded that the map is the last tab stop, so a keyboard visitor passes ten controls before reaching it, mitigated by a skip link.

- [ ] **Step 3: Commit**

`docs: the manual accessibility pass, including what it failed`

### Task 8: Deploy, gated on everything above

**Files:**

- Modify: `.github/workflows/ci.yml` or create `.github/workflows/deploy.yml`
- Modify: `README.md`

The architect chose this over Cloudflare's Git integration so that a red build cannot reach the internet. The workflow must reflect that: deploy runs only on `push` to `main`, and only `needs:` the job that runs every check.

- [ ] **Step 1: Write the deploy job**

`cloudflare/wrangler-action` pinned to a SHA, publishing `dist`. It reads `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` from repository secrets.

- [ ] **Step 2: Write down what the architect has to do, exactly**

In `README.md`, because this is the one part of the project that cannot be automated and must not be guessed at:

- Create a Cloudflare account (free) and a Pages project.
- Create an API token with the **minimum** permissions the deploy needs, naming them precisely.
- Add `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` as repository secrets.

**Do not ask for the token, do not accept it if offered, and do not attempt any of these steps.** Write the instructions and stop.

- [ ] **Step 3: Make the workflow degrade honestly**

Until the secrets exist the deploy job cannot run. It must **skip with a clear message**, not fail — a permanently red badge on an otherwise healthy repository teaches everyone to ignore the badge. Guard on the secret being present and say in the log what is missing.

- [ ] **Step 4: Commit**

`ci: deploy to Cloudflare Pages, only when everything is green`
